# KV准入余量：框架候选，仅CPU准备

当前正式16K运行中观察到约39–40条活跃序列、678176-token容量及非零抢占。原生scheduler_reserve_full_isl=True只要求当前完整输入能装下，不预留所有未来生成token。现有原生watermark默认0，只对已有任务时的waiting/preempted准入保留空闲块，正常running请求不受此准入余量限制。

候选复用原生watermark=1/16：此容量约42386-token余量；纯均匀16K输入的静态容量由41降到38，38×1024输出小于该余量。这只是内存账本示例，不是调度仿真或收益预测。4K/C64本来远低于容量，也不能据此声称吞吐等价。

独立hook在已验证4096默认预算的相同配置边界组合设置，不改已验证源。8项CPU检查执行实际安装的默认参数AST，覆盖control、目标模型、其他vendor/model/parallel、已有正watermark、明确4096预算以及两层默认值异常回滚。没有GPU、服务、Math或benchmark验证，尚未采用；只有后续同工作负载对照能判断减少抢占是否值得降低并行量。与所有其他候选分别验证。
