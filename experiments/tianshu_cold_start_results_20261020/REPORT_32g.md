# 天数：真实 loader 线程与 GPU 静态打包对照

结论：把加载期 CPU 线程从默认 56 限制到 4，模型加载从 146.13 秒降到 15.66 秒；再把静态量化放在 GPU 上，降到 11.54 秒。服务从进程启动到 API ready 从 210.87 秒降到 75.08 秒，约减少 64.39%。加载后恢复原线程数，稳态小规模吞吐没有有意义差异。

| 模式 | 加载期线程 | 权重打包秒 | load_model 秒 | API ready 秒 | 小规模 total tok/s | 小规模 TTFT ms | 后两轮波动 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 默认 CPU 打包 | 56 | 142.684 | 146.130 | 210.875 | 5309.14 | 11543.71 | 0.0484% |
| 4 线程 CPU 打包 | 4 | 12.212 | 15.659 | 81.088 | 5311.56 | 11575.20 | 0.0967% |
| 4 线程 GPU 打包 | 4 | 8.304 | 11.541 | 75.083 | 5309.56 | 11532.38 | 0.0954% |

三组各一个全新服务进程、三轮 4K/1K C64 N64，第一轮排除小规模均值。CPU4/GPU4 相对默认 loader 耗时分别减少 89.28%/92.10%，API ready 分别减少 61.55%/64.39%。GPU4 相对 CPU4 的 loader 再减少 26.30%。默认线程组 v1 的历史加载测量为 129.47 秒，说明单次加载耗时也有环境波动；此处不把三个单次启动当作重复启动的统计分布。

这是进程级冷启动；保留系统文件页缓存和已有 Triton 编译产物，所有组都使用 VLLM_DISABLE_COMPILE_CACHE=1，禁止复用 vLLM AOT 代码。没有声称清空所有系统缓存后的首次安装/编译时间。

## 完整性

独立复查全部 329 项相同运行时来源和每组 snapshot、59 项实际环境与原始 13 项 serve argv。三组 43 bank 的原始 BF16、INT8、scale 共 129 组完整签名都与已合格 Math 的实际 bank 完全相同。原始 BF16 GPU 权重保留，额外 1,326,938,112 字节 INT8 payload 在真实加载 profiler 内计账。线程均恢复为 56，576/576 请求成功，无 preemption、无未释放 future KV reservation，首轮后无现场 autotune。

实际 KV blocks 为 40723 / 40731 / 40731，差异 8 blocks，不把它当作新的 KV 容量优化。三个模式都继续执行 10 月 14 日已采用的 reflect_one 目标表 SQL 反射，不重复计算这项旧优化的收益。

## 采用范围

后续新实验统一使用 GPU4 加载，以减少每次重启等待。该更改保留同一实际权重 payload 与运行期数学路径；本实验未重新跑 Math，也不是正式 N256 吞吐结果。不能把此处 N64 的 TTFT/吞吐替换正式报告。既有正式最好仍是 5375.50 total tok/s、1075.10 output tok/s、4191.14 ms，Math 100/105；对应 release tag 保持不变。
