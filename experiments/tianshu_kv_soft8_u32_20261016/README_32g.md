# 软件8位KV：只改变解码整数中间位宽

前轮软件E4M3/scale1over16编码已通过全部256码GPU解码和4个attention阶段，但tile16/w1仅比BF16快0.90%/1.38%，寄存器244对85，tile32/w2发生125 spill，写入尚未计入，不值得模型接入。新假设仅改位操作中间量uint16→uint32，保留最终uint16→BF16 bitcast、所有格式/舍入/scale/零处理及输入输出值。不能由高寄存器数量断言瓶颈，须再测。

独立新目录动态引用并固定旧codec.py SHA，生成源在旧生成文本唯一一行改cast（可逆），producer/reducer AST不变。原BF16、同次旧u16-t16w1、u32-t16w1/w2和u32-t32w2五配置；4K/5K页交错、两个输入阶段清输出重放Graph、自身FP32/CPU参考与全部256码实际GPU检查。两种wordwidth在相同tile16/w1还须attention输出逐位一致。编译/资源失败逐项记录，不靠排除数值失败通过。写入/真实allocator/校准/模型/Math/服务都未做，绝非正式成绩。只在前一个服务GPU退出后串行运行，23:58停止，不改旧冻结源与最佳版本。

首次GPU launch后另存所有可取得的编译文本/二进制及SHA（warmup内，事件计时前），用于区分中间量宽度、寄存器/溢出和实际编译结果。未支持的非str/bytes项不序列化；若两版最终指令相同，不将源码位宽差异当实际优化。下一项排队器已在probe尚未启动时停止，避免修改和启动竞争，待新源码同步后新排队器继续串行。
