# Tianshu SQL target-reflection CPU experiment

Read-only reference: Ca1iber/flagos-ops-lib commit 8eb57f17d5a3a93f7399af440d8dc319b0916c00. Native source is copied from the current Tianshu FlagGems file; candidate is copied byte-for-byte from that upstream commit with its Apache license. Only the build_sql_model_by_db AST differs. The experiment never imports/initializes the GPU backend, never modifies the live FlagGems source, and never writes the live cache DB.

AST-extract the actual methods to avoid GPU initialization. Exercise composite keys, BIGINT >2^32, BOOLEAN, NULL, hyphenated table names, missing/empty/unmapped tables, and unrelated-table reflection. SQLite read-only backup API snapshots the real Triton3.6 cache. Compare every real table's schema, primary keys and all configuration values; independently query the snapshot using sqlite3 and recompute every row hash.

The first attempt found 1158 tables. It was explicitly stopped during the first full native reflection, before formal benchmark requests started; original code and log are retained at /workspace/benchmark-results/20261020_sql_target_reflection_CPU_tianshu. Repeating an entire native database reflection for every target table would be redundant. v2 performs one actual native full reflection, uses that same real ORM registry for all-table parity, then reflects every candidate table separately. The first target has one directly paired, instrumented latency observation and SQL statement counts; this is explicitly a single sample. Candidate-only repeated timings use seven samples on three representative mapped tables. No repeated baseline latency claim is made.

v2 waits for the exact W8A8 pipeline and subsequent GateUp GPU component to terminate and checks GPU idle. Snapshot DB/logs stay in the container. Git stores code, report and key JSON. This is a cold configuration reflection experiment, not a steady-state inference throughput result. Current frozen GPU runtime is unchanged; no runtime adoption is claimed.
